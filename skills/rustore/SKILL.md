# RuStore: публикация приложения через API

Навык опирается на плагин `dsh-rustore`: он регистрирует инструменты `rustore_*` в DSH и тот же
набор как MCP-сервер (`mcp__rustore__*`). Полный конспект документации — `docs/rustore-api-reference.md`
в рабочем каталоге, исходные тексты — `.artifacts/rustore-docs/txt/`.

## 1. Настройка (токен живёт 900 секунд)

RuStore не выдаёт долгоживущий токен: JWE выпускается из `keyId` + приватного ключа и живёт
**900 секунд**. Поэтому в настройках плагина хранят ключ, а токен плагин выпускает сам и обновляет
за минуту до истечения.

Где взять ключ: RuStore Консоль → вкладка «Компания» (для физлица — «Разработчик») → **API RuStore** →
«Создать ключ». Указать приложения и методы API, нажать «Сгенерировать ключ», скопировать **приватный
ключ** (Base64) — он показывается один раз. Рядом в таблице виден **ID ключа** (`keyId`).
Ключ привязан к компании, а не к сотруднику: при увольнении носителя ключ надо заменить.

Порядок источников настроек (первый непустой побеждает):
конфигурация плагина → секрет DSH (`RUSTORE_PRIVATE_KEY` в Settings → credentials) → переменные
окружения `RUSTORE_*` → файл `%USERPROFILE%\.dsh\rustore.json`.

Ввести ключ проще всего в интерфейсе: **Plugins** → пакет **RuStore** → строка `rustore` (страница плагина) — поля
«ID ключа (keyId)» и «Приватный ключ», кнопки «Сохранить» и «Проверить авторизацию». Записанное
попадает в файл `%USERPROFILE%\.dsh\rustore.json` и применяется сразу.

Проверка:

```
rustore_settings_get            # режим авторизации, keyId, наличие ключа (секреты маскируются)
rustore_auth_check              # выпускает токен и читает список приложений
```

Если `authMode: none` и пользователь не может открыть интерфейс — попросить ключ и записать:
`rustore_settings_set({ keyId, privateKey })`. Приватный ключ в переписке не печатать и не сохранять
в заметки. Для CI и standalone MCP-сервера те же значения задаются переменными
`RUSTORE_KEY_ID` / `RUSTORE_PRIVATE_KEY` (либо `RUSTORE_TOKEN`, если токен уже выписан).

Методы API в ключе должны включать всё, что вызывает навык: список приложений, версии, загрузку
файлов, иконки, скриншоты, настройки публикации, модерацию, архивирование, удаление. Иначе сервер
ответит «нет доступа» на конкретный вызов, хотя авторизация прошла.

## 2. Порядок публикации

Шаги выполняются по порядку; `versionId` из шага 3 нужен всем последующим.

1. **Приложение.** `rustore_apps_list({ appName | appPackage })` — существует ли приложение.
   Если приложения нет, его создают в веб-консоли RuStore: Publishing API работает с версиями
   существующего приложения, а не создаёт приложение.
2. **Категории.** `rustore_categories_list({ appType: "MAIN" | "GAMES" })` — выбрать код категории
   (до двух, обе одного типа). `MAIN` — обычные приложения, `GAMES` — игры.
3. **Черновик.** `rustore_draft_create({ packageName, appName, appType, categories, ageLegal,
   shortDescription, fullDescription, whatsNew, publishType, ... })`.
   Ограничения: `shortDescription` ≤ 80, `fullDescription` ≤ 4000, `whatsNew` ≤ 500,
   `moderInfo` ≤ 180 символов; `ageLegal` — `18+`, `16+`, `12+`, `7+`, `3+`;
   `publishType` — `INSTANTLY`, `DELAYED` или `MANUAL`.
   Ответ содержит `versionId`.
4. **Файл сборки.** `rustore_upload_aab({ packageName, versionId, filePath })` для AAB (рекомендуется)
   или `rustore_upload_apk(...)` для APK. `isMainApk: true` — основной файл; APK с сервисом HMS не
   считается основным.
5. **Иконка.** `rustore_upload_icon({ packageName, versionId, filePath })` — 512×512 px, до 3 МБ,
   фон по всей площади без прозрачных краёв.
6. **Скриншоты.** `rustore_upload_screens({ packageName, versionId, filePaths, orientation, type })` —
   один файл на запрос, порядковый номер 0…9, `type`: `SCREENSHOT` (телефон),
   `TABLET_SCREENSHOT`, `TV_SCREENSHOT`; `orientation`: `PORTRAIT`/`LANDSCAPE`; jpg/png до 5 МБ.
   Для каждого типа устройства — **не менее трёх** скриншотов. Порядок проверяется
   `rustore_screens_list`, лишний удаляется `rustore_screenshot_delete`.
7. **Проверка.** `rustore_version_info` и `rustore_version_status` — что заполнено, чего не хватает.
   Если править текст: `rustore_draft_update({ packageName, versionId, fields: {...} })`
   (API v2, PATCH; `appName` ≤ 50 символов).
8. **Модерация.** `rustore_send_to_moderation({ packageName, versionId, priorityUpdate? })` —
   `priorityUpdate` 0…5 (0 по умолчанию). После отправки статус проверять
   `rustore_version_status`; отказ модератора приходит с причиной.
9. **Публикация.** Зависит от `publishType`:
   - `INSTANTLY` — выходит сразу после модерации, ничего вызывать не нужно;
   - `DELAYED` — дата задаётся `rustore_publish_settings({ publishType: "DELAYED", publishDateTime })`;
   - `MANUAL` — версию, прошедшую модерацию, выпускает `rustore_manual_publish(...)`.

Служебные действия: `rustore_version_archive` (только `READY_FOR_PUBLICATION` и
`REJECTED_BY_MODERATOR`; для `DRAFT`/`PUBLISHED` API откажет), `rustore_draft_delete`
(необратимо, удаляет файлы и медиа).

## 3. Требования к карточке

| Поле | Ограничение |
| --- | --- |
| `appName` | название версии; при правке через v2 — до 50 символов |
| `shortDescription` | до 80 символов |
| `fullDescription` | до 4000 символов, в вёрстке сворачивается до 2000 |
| `whatsNew` | до 500 символов |
| `moderInfo` | до 180 символов, видит только модератор |
| `ageLegal` | 18+, 16+, 12+, 7+, 3+ |
| `categories` | максимум 2 кода, уникальные, одного типа приложения |
| Иконка | 512×512 px, до 3 МБ, фон по всей площади |
| Скриншоты | ≥ 3 на тип устройства, 1–10 за загрузку, пропорции приводятся к 16:9 |
| ТВ-версия | если есть ТВ-файл: краткое/полное описание, «что нового», иконка, скриншоты |

Чего в API нет и что делается в веб-консоли: создание самого приложения, контакты разработчика,
политика конфиденциальности, тестовые доступы, видео и FAQ карточки, отдельная ТВ-иконка.

## 4. Правила безопасности

- Перед `rustore_send_to_moderation`, `rustore_manual_publish`, `rustore_version_archive` и
  `rustore_draft_delete` — подтверждение пользователя; это внешние необратимые действия.
  Черновик и загрузка файлов безопасны.
- Приватный ключ и токен не выводить в ответах, логах и заметках. `rustore_settings_get` показывает
  только маску.
- Не публиковать сборку, которую пользователь явно не просил публиковать; по умолчанию — довести
  до черновика и показать, что осталось.

## 5. Ошибки и диагностика

| Симптом | Причина и действие |
| --- | --- |
| `CONFIG` | нет ни токена, ни `keyId` + приватного ключа: `rustore_settings_get`, затем `rustore_settings_set` |
| `AUTH_FAILED`, `Signature encode error` | ключ скопирован не полностью (пробелы, обрезанная строка) или не совпадает с `keyId` |
| HTTP 401/403 | методы не включены в ключе, ключ отозван или заменён в консоли |
| HTTP 404 на методе | документация RuStore разносит методы по двум хостам; чтение автоматически повторяется на зеркале, для изменяющих запросов сменить `apiBase` в настройках |
| «Загрузите хотя бы один основной APK-файл с сервисом отличным от HMS» | загружен только HMS-APK: нужен основной файл |
| архив отказан | версия в статусе `DRAFT` или `PUBLISHED` — архивировать можно только `READY_FOR_PUBLICATION`/`REJECTED_BY_MODERATOR` |

Токен перевыпускается автоматически; если ошибка авторизации повторяется, проверять ключ в
консоли, а не токен.
